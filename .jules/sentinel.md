## 2025-02-14 - Fix length-based timing attack in authorization
**Vulnerability:** The codebase implemented constant-time string comparison for authorization tokens using `timingSafeEqual`, but the implementation early-returned if the token lengths did not match (i.e. `x.length===y.length && timingSafeEqual(x,y)`). This exposes the actual secret token's length through a timing attack because length mismatches return faster than matching lengths.
**Learning:** Using `timingSafeEqual` does not prevent timing vulnerabilities if there are early returns based on length prior to the constant-time check. An attacker can iteratively guess the required length by measuring response times.
**Prevention:** Ensure constant-time string comparisons always perform the same amount of work regardless of the input length by using a dummy comparison (e.g. comparing the target buffer against itself) when lengths don't match, while still returning false.

## 2025-02-14 - Fix Cross-Site Scripting (XSS) in frontend feed UI
**Vulnerability:** The application frontend renders incoming log messages into the DOM by concatenating HTML strings via `innerHTML`. In `apps/console/public/app.js`, the log item's text was escaped correctly, but the class name (`l.type`) was directly injected without escaping. This exposes the application to XSS if an attacker can control the log stream payload (e.g. log injection via an unverified provider response).
**Learning:** Even when the primary content field is escaped, secondary attributes like class names or style tags within the same `innerHTML` assignment can be an XSS vector if they are derived from external data.
**Prevention:** Consistently use HTML escaping functions (like `esc()`) on *all* data fields injected into HTML templates, regardless of whether they populate visible text or HTML attributes.

## 2025-02-14 - Fix length-based timing attack in token length mismatch fallback
**Vulnerability:** The previous implementation of the token timing attack protection used `timingSafeEqual(x, match ? y : x)` which falls back to comparing the attacker's input `x` against itself when lengths don't match. This means the execution time remained proportional to the attacker's string length (`x.length`), which allows an attacker to repeatedly guess the length until the comparison time changes, thus discovering the true token length.
**Learning:** Comparing user input against itself as a fallback in `timingSafeEqual` re-introduces a length-based timing vulnerability, just in a different place. The time taken is still variable and controlled by the attacker.
**Prevention:** Always ensure constant-time string comparisons execute in time proportional to the true secret's length (`y.length`), not the attacker's input length. If lengths do not match, the secret should be compared to itself: `timingSafeEqual(y, match ? x : y)`.
